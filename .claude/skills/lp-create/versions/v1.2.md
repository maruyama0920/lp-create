# lp-create（競合リサーチ〜Q&A〜完成HTMLまで一括で行うLP作成スキル）

> **バージョン: 1.2**（2026-07-29）。過去バージョンは [`versions/`](versions/) 配下に `v1.0.md`, `v1.1.md`, `v1.2.md` として保存。変更履歴は本ファイル末尾の「更新履歴」を参照。

Claude Codeでは `/lp-create [タイトルや商材の説明]` の形で明示的に呼び出せる。引数なしで `/lp-create` とだけ入力された場合は、直前の会話や現在のプロジェクトから作りたいLPの情報を探し、なければユーザーにタイトル・商材情報を尋ねる。

ユーザーから作りたいLP（ランディングページ）のタイトルや商材情報を受け取ったら、競合・同業他社のLPを自動でリサーチし、構成パターンと配色・雰囲気の傾向の両方を踏まえた提案を行い、短いQ&Aで方向性を確認したうえで、完成した1ファイルのHTML LPまで一気通貫で作る。構成案だけを出して止まるスキルではない——ユーザーが承認すれば、その場でファイルを完成させるところまでが標準フロー。

## 全体の流れ

1. **入力の整理**
   - ユーザーが渡してきたタイトル・商材説明から、業界/ジャンル、想定ターゲット、商材の種類（SaaS, EC, 教育, 士業, 医療, 採用など）を推測する。
   - 情報が薄い場合も止まらずに進める。タイトルだけで業界を推測し、推測した内容を最初に一行で明示する（例:「〇〇というタイトルから、BtoB SaaSの資料請求LPと解釈して進めます」）。

2. **競合・同業サイトのリサーチ（web_search / web_fetch を使用）**
   - 検索クエリは短く具体的に（2〜6語）。例:
     - 「[業界] LP 事例」
     - 「[商材カテゴリ] ランディングページ」
     - 「[競合と思われる企業名] 公式サイト」
     - タイトルに固有の商材名がある場合は、その商材の直接競合も検索する。
   - 目安として3〜6件程度、実際にページを開いて構造を確認できるサイトを探す。検索結果のスニペットだけで判断せず、有力な候補は web_fetch で実際に開く。
   - 日本語商材なら日本語サイトを優先しつつ、海外の代表的な事例も1〜2件混ぜると視野が広がる。
   - **開いたサイトは会社名・URL・一言メモ（何を参考にしたか）をその場で控えておく。** 検索結果のスニペットだけで採用したサイトと、実際にページを開いて確認したサイトは区別してメモする（後述のURL一覧提示で「開いて確認済み」か「未確認」かが分かるように）。

3. **構造分析＋デザイン・配色の傾向分析**
   - 各サイトについて、上から順にどんなセクションが並んでいるかを抽出する（例: ヒーロー / 課題提起 / 解決策 / 特徴・機能 / 実績・導入事例 / お客様の声 / 料金 / FAQ / CTA / フッター等）。
   - 個別の文章やコピーをそのまま書き写さない。著作権上、構成パターン・見出しの役割・訴求の型のみを自分の言葉でまとめる（1サイトからの引用は避け、パラフレーズする）。
   - 構造だけでなく、**配色・雰囲気の傾向**も観察してメモする：ベース背景は白系か暗色系か、アクセントカラーの系統（信頼＝青系、緊急・行動喚起＝赤/オレンジ系、安心＝緑系など）、フォントの太さ・雰囲気（力強いゴシック体の直球訴求か、上品な明朝体のブランディング系か）、バッジ・ランキング表記（No.1、〇冠達成等）の有無、他社比較表の有無、料金の見せ方（取り消し線＋割引など）、電話番号や固定CTAの強さ。
   - リサーチしたサイトに共通するパターンと、差別化に使われている珍しい工夫を分けて整理する。

4. **構成案＋デザイン方向性の提案（参考サイトのURL一覧を必ず添える）**
   - 構成案を出す前に、**リサーチで参考にしたサイトの一覧を、会社名・URL・確認できた点（構造／配色どちらの参考にしたか）付きで箇条書きかテーブルで明示する。** URLを省略して「〇〇業界のLPを見たところ」のように抽象的にまとめない——ユーザーが実際にそのサイトを開いて「これは競合として妥当か」を判断できる形にする。
     - 例:
       - [A社](https://example-a.co.jp/lp) — 白背景＋青×赤の直球訴求型。他社比較表とNo.1バッジが特徴
       - [B社](https://example-b.co.jp/) — 構成のみ参考（ヒーロー→実績→料金→FAQの順）
   - スニペットのみで構造を推測し実際には開いていないサイトがあれば、「未確認（スニペットのみ）」等と明記し、確認済みのサイトと混同しない。
   - リサーチ結果を踏まえて、ユーザーのLP向けにセクション構成を提案する。各セクションについて次の3点を書く:
     - **セクション名**（見出しレベル）
     - **狙い**（このセクションが読者に何をさせたいか／どんな心理的ハードルを下げるか）
     - **要点**（ここに入れるべき情報の種類。コピー文そのものではなく、何を書くべきかの指示）
   - 業界内で「ほぼ必須」とされるセクションと、「差別化のためにあると良い」セクションを分けて示すと親切。
   - 併せて、観察した配色・雰囲気の傾向から**この業界で標準的なデザイン方向性**を一言でまとめて提示する（例:「この業界の競合LPは、白背景＋トラストブルー＋レッド系CTAの直球な訴求型が主流」「この業界はむしろ上品な写真主体のブランディング型が多い」等）。
   - **既定の姿勢**: 特に指定がない限り、実際にリサーチした競合の配色・雰囲気に寄せることをデフォルト提案とする（作り手の独自美学より、業界の実物に似せる方を優先）。地方系サービス業・直販・即決を促す商材（駆除・修理・買取・士業の初回相談など）では、白/明るい背景＋信頼色（青系）＋行動喚起色（赤/オレンジ系）＋太いゴシック体＋No.1バッジ＋他社比較表＋強い固定CTAという「直球な反応型LP」の傾向が強く出やすい。SaaS・高級ブランド・ファッション等では上品なブランディング型が主流になりやすい——リサーチ結果に基づいて実際の傾向を優先し、決め打ちしない。
   - 競合が採用していた工夫のうち、ユーザーの商材にも使えそうなものがあれば具体的に触れる（どのサイトかまでは名指ししなくてよいが、パターンとして言及するのはOK）。

5. **Q&Aで方向性を確認（本文生成に入る前に必ず行う）**
   - 構成案とデザイン方向性を提示したら、そのままHTML化に進まず、短いQ&Aでユーザーに確認する。目安として次を確認する：
     1. **提示した参考サイトのURL一覧が妥当か**（見当違いの競合が混ざっていないか、逆に外せない競合が抜けていないか、「未確認」のサイトを実際に開いて確認してほしいか）——ここが崩れていると以降の構成・配色の提案ごと前提が狂うため、最初に確認する。
     2. 構成案（セクション構成）はこれで進めてよいか、増減させたいセクションはあるか
     3. 提案したデザイン方向性（配色・雰囲気）でよいか、それとも別の方向（例: もっと上品に／もっと直球に／特定の競合にさらに寄せたい）を希望するか
     4. 本文コピーの穴埋めに必要な実務情報のうち、まだ聞いていないもの（社名・屋号、電話番号・受付時間、対応エリア、料金・保証内容、実績数値、使いたい写真の有無など）
   - ユーザーが「この会社は違う」「この競合も見て」等、URL一覧に対する指摘をした場合は、2の構成案に進む前にリサーチをやり直す（ステップ2・3に戻る）。
   - AskUserQuestion等で選択式にできる部分（デザインの方向性など）は選択式にすると早い。自由記述が必要な項目（社名・電話番号等）は普通に聞く。
   - ユーザーが「お任せする」「そのままでいい」と言った場合は、提案どおり／推測で補って進めてよい（止まりすぎない）。

6. **画像生成（デザイン方向性が固まった後、HTML実装に入る前に行う）**
   - ステップ5のQ&Aで構成・デザイン方向性が確定した時点で、ユーザーから使える実写真の提供がない場合は、HTML実装に進む前にこのステップで必要な画像を生成する。「写真がなければSVG代替」に安易に倒さず、まず生成を試みる。
   - 画像生成はOpenAI（ChatGPT）の画像生成API（例: gpt-image-1等）を使う。APIキーはプロジェクトルート直下の `.env` ファイルに `openAI=<APIキー>` の形で保存されている前提。
     - まずプロジェクトルートに `.env` があるか、`openAI` キーに値が入っているかを確認する。
     - 存在し値も入っていれば、それを使ってAPIを呼び出し画像を生成する。
     - `.env` が無い、または `openAI` キーが空・未設定の場合は、他の生成手段に無断で切り替えたり黙ってSVG代替に倒したりせず、**「プロジェクトフォルダ直下に `.env` を作成し、`openAI=<APIキー>` の形でOpenAIのAPIキーを用意してください」とユーザーに明示的に依頼して一度止まる。**
   - 生成する画像は、確定した構成案の各セクション（ヒーロー背景／識別・商品写真／課題・リスク訴求写真／最終CTA背景など）に対応させ、ステップ5で確定済みの配色・雰囲気・実在感のレベル（写実的な実写風か、イラスト・グラフィック寄りかなど）に合わせてプロンプトを作る。1枚を複数箇所で色調違いに使い回す構図（例: ヒーロー背景と最終CTA背景で同じ画像を別オーバーレイで使用）も検討してよい。
   - 生成した画像はプロジェクト内に保存し、HTML実装時にbase64埋め込みまたは相対パス参照で組み込む。
   - 実在の人物・企業ロゴ・商標をそのまま写実的に生成しない、著作権的にグレーな既存キャラクター等を模倣しないなど、生成AIの利用規約・権利面に注意する。
   - `.env` のAPIキーの値はチャット・ログ・コミットメッセージなど、いかなる出力にも書き出さない。

7. **完成HTMLの実装（既定の最終成果物）**
   - Q&Aで確認が取れたら、その場で完成した1ファイルのLPをHTMLとして書き出す。構成案の提示だけで終わらせず、ここまでを標準フローとする。
   - 実装時の技術的な型（過去の実装で有効だったパターン）：
     - `<style>` 内でCSS変数によるカラーシステムを組み、`@media (prefers-color-scheme: dark)` と `:root[data-theme="dark"]/[data-theme="light"]` の両方に対応させる（ライト/ダーク双方で破綻しないように）。
     - セクションは `.band` 単位のブロックとして積み、`.container` で最大幅を揃える。
     - スクロールで要素をフェードインさせる`.reveal` + `IntersectionObserver`パターンを使ってよい（`prefers-reduced-motion`配慮も入れる）。
     - モバイル幅では画面下部に固定CTAバー（電話／フォームの2分割など）を出す。
     - 直球な反応型の方向性を選んだ場合は、他社比較表・No.1系バッジ（自社調べの注記付き）・料金の取り消し線＋割引＋人気ランキングリボン・★評価つき口コミ・黄色マーカー風ハイライトなど、このジャンルの定番パーツを構成に組み込む。
     - 写真素材（ユーザー提供、またはステップ6で生成したもの）はbase64で埋め込み、複数箇所（ヒーロー背景／識別写真／リスク訴求写真／最終CTA背景など）で使い回して情報量を増やす。ステップ6を経てもなお画像が用意できない場合（ユーザーがAPIキー用意を見送った等）に限り、SVGアイコンや幾何学パターンで代替し、後から差し替えやすいようコメントで示す。
     - ファイルは既存LPファイルを上書きせず、新規ファイル名（例: `[商材名]-lp.html`）で作成する。既存の別方向性のLPと比較したい場合はそれぞれ別ファイルのまま残す。
   - 完成後は必ずブラウザプレビューで主要セクション（ヘッダー、ヒーロー、比較・実績、料金、最終CTA、モバイル幅）を確認し、崩れがないかざっと見る。

8. **出力**
   - 構成提案・デザイン方向性の説明はチャット内で完結させる（report風の見出し立てにはせず自然な文章＋箇条書きで良い）。
   - 完成したLPはHTMLファイルとしてプロジェクトディレクトリに保存し、チャットでは変更点の要約を簡潔に伝える。
   - 構成案だけを.mdや.docxとして欲しいと言われた場合は、そちらの形式でも出力する。
   - 最後に、必要なら「特定の競合URLを指定して深掘りもできる」「別の配色パターンをもう1つ作ることもできる」ことを一言添えてよい（過剰な売り込みはしない）。

## Claude Code環境での前提

- このスキルはWeb検索・Webページ取得ツールが使える前提で書かれている。プロジェクトやセッションでWeb系ツールが許可されていない場合は、まずユーザーにその旨を伝え、許可を確認するか、手元のURLを渡してもらう。
- `allowed-tools` を絞っている環境では、Web検索・Web取得系のツールをこのスキル用に許可しておくとスムーズに動く。
- 画像生成（ステップ6）はプロジェクトルート直下の `.env`（`openAI=<APIキー>`）が前提。無い場合は生成をスキップして進めるのではなく、ユーザーに用意を依頼する。

## 注意点

- 検索・取得したサイトの文章を長く引用しない。15語以上の直接引用はしない。要約は自分の言葉で。
- 実在の企業名を挙げること自体は問題ないが、他社のコピーや画像をそのまま複製・転載しない。
- 情報が古い可能性がある業界（トレンドの移り変わりが早いジャンル）は、検索結果の日付にも注意する。
- ユーザーが「もっと絞って」「この会社だけ見て」等の追加指示を出したら、その範囲でリサーチをやり直す。
- HTML実装まで進める場合も、他社サイトのコピー文・画像・独自イラストをそのまま複製しない。構成・配色・パーツの「型」を参考にし、コピーや画像は本スキルの実行内で新規に作る（ユーザー提供の実データ・実写真がある場合はそれを使う）。
- No.1・〇冠達成等のバッジ表現を使う場合は、必ず「自社調べ」等の注記を添える。実在しない受賞・調査を断定的に事実として書かない。
- 一度Q&Aで方向性を確認した後にユーザーから「もっと〇〇寄りに」等の追加調整が入ったら、全体を作り直すのではなく、色・トーン・該当パーツだけを差分修正する。
- `.env` の `openAI` キーの値は、いかなる出力（チャット・ログ・生成ファイル・コミット）にも書き出さない。値の有無や文字数の確認に留め、値そのものを表示・引用しない。
